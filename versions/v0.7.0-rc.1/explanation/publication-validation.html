Publication validation and acceptance gates¶

Status: storage release candidate, October 23, 2026. The measurements below were taken on the publisher before its default Rust/Python/CLI integration. They describe synthetic fixtures, not production performance SLOs or a proof of durability on every local filesystem. The publication protocol remains the same in 0.7.0-rc.1; application integration has separate regression coverage.

Platform correctness¶

The held-open CURRENT regression and the complete feature suite passed on Linux, macOS and Windows at Rust 1.88 for commit ac607d9. Both Windows jobs also passed ten repetitions of the three-reader/twenty-publication stress test. The original failure was real: tempfile’s MoveFileExW-only replacement returned access denied while readers were active. std::fs::rename uses a Windows POSIX-semantics fallback, allowing old handles to retain their bytes while new opens select the replacement. No sleeps or permission-error suppression were added to publication.

All cooperating writers still require the stable writer lock. The tests do not authorize concurrent external replacement or truncation of mapped graph files.

Accepted Windows release scope¶

Decision recorded October 25, 2026: Windows 0.7 ships coherent publication, owned read views and process-crash recovery with best-effort power-loss durability. A power failure may require rebuilding the environment from ontology sources. A successful commit or retention of a previous version does not guarantee that a complete version remains recoverable after power loss. Existing flushing is preserved; directory syncing remains unsupported on Windows. The process-exit CI coverage and the Linux guest results below do not strengthen this Windows contract. See the snapshot guide.

Guest crash durability¶

The disposable QEMU harness completed a nine-case pilot followed by 27 cases across three repeated cycles. It used a 64 MiB ext4 image, a Linux 7.2.6-76070206-generic guest, QEMU 8.2.2 with TCG and cache=none, and a small ontology/configuration/alias fixture in an already initialized environment. The host SIGKILLed QEMU at the selected publication boundary, then booted a fresh guest. Verification mounted the filesystem read-only after ext4’s journal recovery and opened only SnapshotReader, before any application recovery writer.

This establishes a bounded guest kernel/page-cache-loss test for this filesystem/kernel setup. The host and physical device caches were not power-cycled. It does not cover every torn/reordered device write, initialization interruptions, large-store crash cases, other filesystems or Windows/macOS power-loss semantics. Directory sync remains a no-op on Windows. Normal-operation and process-exit correctness there must not be advertised as the same durability guarantee as this Linux experiment.

Reproduction instructions are in lib/tests/support/README.md; the machine-readable report is docs/reviews/snapshot-durability-vm-2026-10-23.json. Guest serial logs and disk images remain in the local /tmp artifact directory identified by that report. The harness exposes no host directories, network or physical disks.

Workload measurements¶

The release diagnostic uses local, offline synthetic sources with long hashed literals. Four active reader processes repeatedly query their retained version while the writer makes three separate one-graph commits, followed by one alias-only commit. Readers then refresh and build a new PSO index while retaining their old snapshot/index. A burst staged in one update would have one publication; this experiment deliberately measures three separate publications.

Five fresh-process warm reads were measured per size. The first selective query builds the PSO index; warm selective queries reuse it. A per-file eviction request was also made, but POSIX_FADV_DONTNEED is advisory and does not prove cold storage reads. No host-global cache clearing was performed.

Proposed gates before normal API integration¶

These are historical engineering targets from before integration. Current memory measurements are advisory, not release limits. The accepted Windows contract above supersedes any stronger implication from these proposed gates; the power-loss campaign applies only to its tested Linux configuration.

Correctness gates are strict: no mixed versions, no failed cooperating publications under the tested concurrent-reader workload, retained views stay unchanged, and failed refresh preserves the old view. Acknowledged commits must survive the defined durability campaign; a single loss or incomplete selected version fails that gate. Keep platform durability claims tied to tested/specified flush behavior.

For initial engineering work at roughly 20 MiB with four active readers, use these provisional budgets, subject to workload/product review:

  • Graph-changing commit: under one second in the diagnostic workload.

  • Refresh: under 100 ms, plus under 100 ms for the first selective query/index.

  • Writer peak RSS: under 256 MiB; reader peak RSS under 128 MiB for one indexed version and under 256 MiB when deliberately retaining two.

  • Retention: continue to expose/document full-store growth per graph-changing commit. Do not enable automatic deletion without a process-safe reader protocol.

The target fixture fits these provisional budgets; the larger fixture crosses some of them. They are not new public latency/memory promises or statistically validated p95 thresholds. Revisit them with real ontology/query workloads before making the new publisher the default or expanding its supported durability scope.

Ownership follow-up and initial Rust integration¶

The focused ownership review found no cycle requiring a new release mechanism. Weak-reference tests check that ordinary refresh frees unreferenced old metadata and RDF5D snapshots, while owned query iterators retain their RDF backing until dropped. Cloned handles share a snapshot, and metadata-only refresh now preserves the same mapped RDF5D object and its whole-store indexes. Scoped View indexes remain view-local to preserve scope-specific property-path semantics.

Ordinary refresh includes destruction of the old state; retained-view refresh defers that work. All four release-mode workers confirmed the old RDF snapshot was destroyed before building the new index. File retention remains unchanged. This is one diagnostic run per mode with independent equivalent fixtures, not a controlled latency/memory guarantee. Raw worker reports, commands and hashes are in docs/reviews/snapshot-ownership-2026-10-23.json.

The initial explicit integration added OntoEnv::create_snapshot, OntoEnv::open_snapshot and OntoEnv::open_snapshot_writer, returning specialized reader/writer handles. The 0.7 release candidate additionally uses the publisher through the normal Rust, Python and CLI APIs, including recursive source updates, explicit migration and independently owned Python query views. Regression tests cover nested rollback/unwinding, bounded imports, coherent reader refresh, recreation, in-flight dataset iterators, copied roots and release upgrades. A writer-lock guard explicitly unlocks before closing so inherited descriptors from concurrent process spawning cannot prolong a dropped writer’s lock.

Avoid implicit refresh of retained views: their stable identity is the consistency guarantee. Per-graph disk COW would not directly remove per-process in-memory query indexes and is not justified by these measurements alone. Safe online file cleanup remains future work.

Default backend release candidate¶

The 0.7.0-rc.1 integration passed local validation on October 23, 2026:

  • cargo test --workspace --release --offline: 240 passed, including doctests; seven process helpers/examples remained intentionally ignored.

  • cargo clippy --workspace --all-targets --all-features --offline -- -D warnings and cargo fmt --all -- --check: passed.

  • The release abi3 wheel built successfully; its complete Python 3.14 suite passed 165 tests. The 21 warnings were existing deprecation warnings from rdflib and compatibility APIs. The pyontoenv shim import test also passed.

  • A fresh environment created by the released 0.5.5 wheel migrated through the new wheel. Stored triples survived, legacy file contents remained intact, and ordinary open refused the old format before explicit migration.

  • Sphinx rebuilt with warnings treated as errors; workspace version checks and diff whitespace checks passed.

The additional tests exercise ordinary import/update/rename publication, configuration changes with deliberately bounded imports, rollback and unwinding, reader refresh, retained graph/closure/dataset views, explicit dataset rebinding with an outstanding iterator, migration/recovery, copied publication roots, logical recreation, and config/reset root selection through ONTOENV_DIR. Staged graph contents are shared through Arc across nested checkpoints and publication preparation; graph-copy APIs still allocate their requested copies.

These local results do not replace the Linux/macOS/Windows CI matrix for the new default integration. The earlier VM crash and workload measurements above exercise the underlying publisher, not the complete new API facade. No new power-loss or performance guarantee is inferred from the integration tests.
